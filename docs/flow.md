# Маршруты заявки

Рабочая версия начинается с webhook, который получает заявку с сайта. Дальше workflow проверяет условия и выбирает ветку обработки. Отдельный Telegram Trigger принимает сообщения и нажатия кнопок от исполнителей.

По рабочему экспорту видны следующие действия:

1. Исполнитель отмечает в Telegram, свободен он или занят. Это меняет его статус в Google Sheets.
2. Система отправляет предложение по заявке. Ответы исполнителя разбираются по веткам: взять, пропустить, отменить.
3. При ответе обновляются сообщение в Telegram и записи в таблицах.
4. Ветка Wait возвращается к заявке через 10 минут и проверяет её состояние. Само наличие этой ветки не доказывает гарантированную доставку или отсутствие повторов.

В workflow 64 узла. Большая часть графа приходится на Telegram, таблицы, условия и переключатели. Два Code nodes форматируют данные для сообщений. Их наличие не означает, что основная логика написана на JavaScript: маршруты собраны в n8n.

## Прототип с очередью

Во втором экспорте 107 узлов. Там добавлены выбор первого исполнителя в очереди, поиск строки очереди, предложение следующему и ветки ожидания. Этот экспорт неактивен. Я показываю его как направление развития системы, а не как проверенную в работе функциональность.

## Почему здесь нет полного экспорта

В исходных файлах есть привязки к аккаунтам и сохранённые данные запусков. Публиковать их вместе с проектом клиента нельзя. Файл `workflow/architecture.json` сохраняет граф рабочей версии, но удаляет настройки всех узлов. Это позволяет изучить схему без доступа к данным клиента.
